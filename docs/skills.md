# مهارات وكيل عمليات المكتب

## المستخدم والمشكلة والنتيجة
- **المستخدم المستهدف:** موظفو مكتب الخدمات العامة ومديره (وليس العملاء؛ العملاء يخدمهم وكيل واتساب).
- **المشكلة:** متابعة عشرات العملاء والمعاملات والمستندات يدوياً تؤدي إلى فوات مواعيد تجديد (إقامات، رخص عمل، تأكيد السجل)، وتوقف معاملات بانتظار مستندات دون متابعة، وإجابات غير موحدة عن المتطلبات.
- **النتيجة المطلوبة:** ألّا يفوت موعد تجديد أو تتوقف معاملة دون أن يعرف المكتب. كل إجراء خارجي (رسالة للعميل، تغيير حالة) يمر باعتماد بشري، ومصدر كل معلومة واضح.

## المهارات الأساسية (الأساس المشترك قبل التخصص)
ما يجعل الوكيل يفهم مهمته ويتصرف بمنطق موظف خبير، بغض النظر عن المجال.

| # | المهارة | كيف تعمل | ما يضمنه الكود (لا يعتمد على النموذج) | الاختبار |
|---|---|---|---|---|
| أ١ | فهم الطلب | يصوغ ما فهمه في جملة (`understood_request`) قبل الإجابة، وتظهر للموظف «فهمت طلبك: …» | الإجابة بلا صياغة للفهم تُرفض ويُطلب تصحيحها | `basic-skills.test.js` |
| أ٢ | فهم اللهجة والأخطاء الإملائية | تعليمات + مرادفات عامية في البحث + بحث أسماء يتجاهل الهمزات والتطويل ويتسامح مع حرف خطأ | «احمد» = «أحمد»، «الشمرى» = «الشمري»، «فهـد» = «فهد» | ✓ |
| أ٣ | تذكّر المحادثة | كل محادثة تحفظ الأدوار السابقة مع الكيانات المذكورة بمعرّفاتها؛ «هو» و«المعاملة الثانية» تُفهم منها | المحادثة خاصة بصاحبها؛ آخر ٨ أدوار (`AGENT_HISTORY_TURNS`) | ✓ |
| أ٤ | السؤال التوضيحي | عند غموض يغيّر النتيجة يسأل سؤالاً واحداً بخيارات، ولا ينفذ | `find_client` يعلن `ambiguous`؛ الحالة `needs_clarification` لا تُحوَّل للمدير ولا تنفذ كتابة؛ السؤال يُحفظ ليُفهم الجواب التالي | ✓ |
| أ٥ | فهم التواريخ | `resolve_date`: بكرة، بعد ٣ أيام، الخميس الجاي، الأسبوع الجاي، نهاية الشهر، ١٥ رجب، ١ رمضان ١٤٤٨، ٣ ديسمبر، صيغ رقمية | حساب ثابت بتوقيت الرياض وأم القرى؛ التعبير غير المفهوم يعيد خطأ يطلب إعادة الصياغة | ✓ ١٦ صيغة |
| أ٦ | التخطيط متعدد الخطوات | يقرأ قبل أن يكتب، ويتحقق من النواقص قبل تجهيز تذكير بها، وينفذ كل الخطوات | حد أقصى للخطوات مع تحويل للموظف | ✓ |
| أ٧ | التمييز بين الحقيقة والاستنتاج والافتراض | يذكر الافتراضات (`assumptions`) ودرجة ثقته (`confidence`)، ويعلن حالة اعتماد كل مصدر | المصادر غير المسترجعة فعلاً تُستبعد | ✓ |
| أ٨ | ترتيب الأولويات | `get_daily_overview`: منتهٍ ← مهام متأخرة ← ينتهي خلال ٧ أيام ← اعتمادات ← معاملات متوقفة | الترتيب محسوب برمجياً | ✓ |
| أ٩ | المراجعة قبل الإجابة | يتحقق أن كل معلومة لها أداة أو مصدر، وأن «تم» مؤكدة | تنبيه آلي إن ادّعى إرسالاً أو تغييراً لم تؤكده الأدوات | ✓ |
| أ١٠ | قبول التصحيح | «لا، قصدي سالم» يُلغي الافتراض السابق | الذاكرة تحفظ الدور السابق | تقييم |
| أ١١ | معرفة الحدود والصلاحيات | يحوّل للمدير عند نقص المعرفة أو الخصم أو الشكوى؛ يرفض تجاوز الصلاحيات ويتجاهل التعليمات المدسوسة | الصلاحيات في المنفّذ؛ تحويل آلي إن قرر الحاجة لموظف | ✓ |

### قياس جودة المهارات بالنموذج الحقيقي
الاختبارات أعلاه تضمن سلوك النظام، لكن جودة الفهم والمنطق لا تُقاس إلا بالنموذج الحقيقي. لذلك:
- `evals/basic-skills.json`: ١٧ سيناريو (لهجة، تواريخ نسبية وهجرية، غموض ثم توضيح، ذاكرة، تصحيح، خطوات متعددة، فجوة معرفة، معلومة غير موثقة، خدمة خارج الكتالوج، خصم، تعارض بيانات، صلاحيات، تعليمات مدسوسة، عميل غير موجود).
- `npm run eval` يشغّلها ويصححها آلياً ويحفظ تقريراً في `data/`. **يتطلب `ANTHROPIC_API_KEY` وله تكلفة فعلية** (بالنموذج الافتراضي تقديرياً ١–٣ دولارات للتشغيلة الواحدة؛ الاستهلاك الفعلي بالرموز يظهر في نهاية التقرير).
- استخدمه لمقارنة النماذج (`LLM_MODEL`) ومستويات الجهد (`LLM_EFFORT`) قبل اعتماد أحدها، وبعد أي تعديل على التعليمات.

## المهارات التخصصية (النسخة الأولى)

«متخصص وملم بالمجال» = المهارات التالية القابلة للاختبار:

| # | المهارة | المدخلات | المعرفة | الأداة | المخرجات | معيار النجاح (مُختبر) |
|---|---|---|---|---|---|---|
| 1 | العثور على العميل وقراءة ملفه | اسم / جوال / سجل / آخر ٤ أرقام | — | `find_client`, `get_client` | بيانات مختصرة + مستندات بأيام متبقية + معاملات | الأيام تحسب برمجياً؛ الجوال مختصر؛ لا وصول لعميل منشأة أخرى (`tools.test.js`) |
| 2 | قراءة معاملة | رقم المعاملة | حالات المعاملة | `get_transaction` | الحالة، المستلم، الأحداث، الحالات التالية المسموحة | معاملة منشأة أخرى = غير موجودة |
| 3 | فحص النواقص | رقم المعاملة | متطلبات الخدمة (`services.json`) | `check_missing_requirements` | قائمة النواقص + المصدر + حالة اعتماد المتطلبات | يطابق النواقص الصحيحة؛ الخدمة بلا متطلبات موثقة لا تُخترع لها نواقص |
| 4 | متابعة الانتهاءات | عدد الأيام، نوع المستند | `document-types.json` | `list_expiring_documents` | مستندات مرتبة بالأيام المتبقية مع الهجري ومصدر التاريخ | حساب صحيح بتوقيت الرياض، يشمل المنتهي |
| 5 | الإجابة من المعرفة | سؤال | كل ملفات `knowledge/` | `search_knowledge` | نتائج بمعرّف وحالة اعتماد ومصدر | يجد الخدمة بالعامية («الإقامة»، «كفالة»)؛ لا نتائج لما ليس في المعرفة (`kb.test.js`) |
| 6 | إنشاء مهمة داخلية | عنوان، استحقاق، أولوية، ارتباطات | — | `create_task` | رقم المهمة | التكرار لا ينشئ مهمة ثانية |
| 7 | تجهيز تذكير للعميل | عميل، نوع، مستند/معاملة، قناة | قوالب الرسائل، سياسة الإيقاف | `prepare_reminder` | تذكير + إجراء إرسال **ينتظر اعتماداً** | لا يُرسل قبل الاعتماد؛ الموقف للرسائل يُتخطى؛ اليدوي لا يُعلَّم «أُرسل» |
| 8 | تحديث حالة معتمد | معاملة، حالة جديدة، سبب | آلة حالات المعاملة | `propose_transaction_status` + اعتماد | إجراء ينتظر اعتماد مدير، ثم تنفيذ | انتقال غير مسموح يُرفض؛ تغيّر الحالة بعد الاقتراح = تعارض لا كتابة فوقها؛ الموظف لا يعتمد |
| 9 | تسجيل النتيجة | معاملة، نتيجة، مستندات مستلمة | — | `record_outcome` | حدث في سجل المعاملة | المعاملة المغلقة ترفض التسجيل |
| 10 | التحويل للمختص | سبب، ملخص | الحالات الموثقة | `escalate_to_staff` | مهمة للمدير | إن قرر الوكيل الحاجة لموظف ولم يحوّل، يُحوَّل برمجياً (`agent.test.js`) |
| 11 | المتابعة الآلية | — (يومياً) | مواعيد التذكير لكل نوع | `runFollowups` (قواعد ثابتة، بلا نموذج) | حالات مستندات، تذكيرات معلقة، مهام، متابعة المتوقف | إعادة التشغيل لا تكرر؛ مرحلة واحدة لكل تشغيل؛ التجديد يلغي القديم (`followups.test.js`) |

### قواعد عامة مُطبقة برمجياً (لا تعتمد على التزام النموذج)
- الصلاحيات تُفحص في المنفّذ لكل أداة، والأدوات المعروضة للنموذج تُصفّى حسب الدور.
- المدخلات تُتحقق بالمخطط؛ الحقول غير المعروفة (مثل `tenant_id`) مرفوضة.
- المصادر المستشهد بها تُقبل فقط إن استُرجعت فعلاً في هذا الطلب.
- الإجراءات المعروضة للمستخدم من سجل المنفّذ، ويظهر تنبيه إن ادّعى النص إرسالاً لم يحدث.
- فشل النموذج ينشئ مهمة للمدير حتى لا يضيع الطلب.

## أولويات النسخة الأولى
اختيرت المهارات ١–١١ لأنها تغطي أعلى قيمة (منع فوات التجديدات والغرامات، وتسريع المعاملات المتوقفة) وتعمل كلها على بيانات المكتب دون تكاملات حكومية.

## مهارات مؤجلة وما تحتاجه

| المهارة | لماذا أُجلت | المطلوب لإضافتها |
|---|---|---|
| مزامنة الطلبات والعملاء من متجر زد (`shmsaja.zid.store`) كمعاملات | يتطلب رمز API لتطبيق زد في الخادم (المتاح حالياً اتصال قراءة لمساعد التطوير فقط) | رمز Zid API (OAuth) + تحديد حالات الطلب المقابلة لحالات المعاملة؛ الحقل `external_ref` جاهز في الجداول |
| قراءة تواريخ الانتهاء آلياً من أبشر/مقيم/قوى | لا توجد واجهات API عامة؛ الربط يتطلب اشتراكات أعمال رسمية | اشتراك «مقيم» أو تكامل معتمد؛ إلى ذلك الحين يُدخل الموظف التاريخ مع `data_source` و`verified_at` |
| الأسعار وعروض الأسعار | الأسعار غير معتمدة (`reference-prices.json` غير محمّل) | اعتماد المالك لأتعاب كل خدمة؛ حقلا `office_fee` و`gov_fees` جاهزان |
| إرسال تذكيرات النواقص والمتابعة عبر واتساب | لا توجد قوالب Meta معتمدة لهذين النوعين | اعتماد قالبين وضبط `WA_MISSING_DOCS_TEMPLATE` و`WA_FOLLOWUP_TEMPLATE` (حتى ذلك الحين: إرسال يدوي) |
| تتبع تسليم رسائل واتساب (delivered/read) | يحتاج webhook حالات من Meta | ربط حقل `statuses` في webhook وكيل واتساب بجدول `reminders.provider_message_id` |
| قراءة المستندات المرفوعة (OCR) | سياسة المكتب: لا معالجة لصور الهويات عبر المحادثة | قرار المالك + تخزين آمن + موافقة العميل |
| بحث دلالي (embeddings) | الحجم الحالي (~١٧٠ مدخلاً) يكفيه البحث بالكلمات | يُضاف إن أظهر سجل `search_knowledge` أسئلة متكررة بلا نتائج |
| الاعتماد الجماعي للتذكيرات | النسخة الأولى تعتمد تذكيراً تذكيراً | يُضاف عند تجاوز التذكيرات اليومية حداً يُتعب المدير |
