# قاعدة المعرفة

| الملف | المحتوى | من أين | كيف يُعدَّل |
|---|---|---|---|
| `services.json` | ١٣٨ خدمة منشورة (الاسم، الفئة، الجهة، الحالة، المتطلبات، الخطوات) | مولّد من `knowledge.json` و`services-catalog.csv` | عدّل المصدرين ثم `npm run kb:build` |
| `document-types.json` | أنواع المستندات، مواعيد التذكير، حقائق نظامية لكل نوع | محرر يدوياً + مصادر رسمية | يدوياً |
| `policies.json` | سياسات المكتب + سياسات تشغيلية مقترحة | `knowledge.json` + مقترحات | يدوياً |
| `procedures.json` | إجراءات العمل الداخلية | مسودات | يدوياً |
| `faq.json` | أسئلة متكررة | `knowledge.json` | يدوياً |
| `cases.json` | حالات موثقة وطريقة التصرف | مسودات + قواعد معتمدة | يدوياً |
| `business.json` | بيانات المكتب وساعات العمل | `knowledge.json` | يدوياً |

## حقول التوثيق (إلزامية لكل معلومة)
- `source`: اسم المصدر و`url` إن وجد و`kind`: `official` (جهة حكومية) | `office` (قرار المكتب) | `office_catalog` | `press` | `proposal`.
- `checked_at`: تاريخ آخر تحقق (YYYY-MM-DD).
- `approval`:
  - `approved` معتمد، يُستخدم كحقيقة.
  - `needs_approval` يحتاج اعتماد المالك (سياسات وأسعار ومواعيد مقترحة).
  - `needs_verification` من مصدر رسمي لكن تعذر فتح الصفحة وقت التحقق.
  - `unverified` من مصدر غير رسمي، **لا يُقدَّم كحقيقة**.
  - في الخدمات: `provenance.requirements_approval` = `office_unverified` (صاغها المكتب ولم تُطابق مع الجهة) أو `missing` (لا متطلبات موثقة؛ يحددها الموظف).

الوكيل يعرض حالة الاعتماد مع كل مصدر يستشهد به، ولا يقدّم معلومة `unverified` على أنها مؤكدة.

## الفصل بين المعرفة وبيانات العملاء
هذه الملفات معرفة عامة ثابتة. بيانات العملاء والمعاملات والمستندات في قاعدة البيانات (`OPS_DB_PATH`)، ويقرأها الوكيل بالأدوات عند الحاجة فقط ولا تُدمج في التعليمات.

## الاسترجاع
بحث بالكلمات مع تطبيع عربي (الهمزات، التاء المربوطة، الألف المقصورة، «ال») وقائمة مرادفات صغيرة في `src/ops/kb/index.js`. الحجم الحالي (نحو ١٧٠ مدخلاً) لا يحتاج بحثاً دلالياً. يُضاف البحث الدلالي إذا أظهرت سجلات `search_knowledge` أسئلة متكررة بلا نتائج.
